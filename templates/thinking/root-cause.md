# 根因分析模板

问题反复出现，往往是因为只处理了表面症状。这份模板带你从现象逐层挖到根本原因，并验证根因是否成立，确保一次解决到位。

## 一、锁定现象

- 具体现象：【何时、何地、出现什么，用数据描述】
- 影响范围：【涉及哪些人、哪些环节，损失多大】
- <span class="sn-blue" data-sisenote-color="blue">概念：现象是可观察的事实，根因是导致现象的深层机制</span>

## 二、鱼骨图分类归因

从「人、机、料、法、环、测」六类穷举可能原因：

| 类别 | 可能原因 | 证据 |
|---|---|---|
| 人（人员） | 【填写】 | 【填写】 |
| 法（方法） | 【填写】 | 【填写】 |
| 机（设备） | 【填写】 | 【填写】 |

- <span class="sn-green" data-sisenote-color="green">思路：每一类至少写一个原因，写不出也要标注「暂无」，防止视角遗漏</span>

## 三、深挖根本原因

- 直接原因：【填写】
- 上一层原因：【为什么会发生，填写】
- 根本原因：【再问一次为什么，直到触及可改变的机制】
- <span class="sn-red" data-sisenote-color="red">重点：根因必须是「可被干预」的，归到「运气不好」不算根因</span>

## 四、验证根因

- 验证方法：【填写一个小实验或数据核对】
- 若消除该因，现象是否消失？☐ 是 ☐ 否
- <span class="sn-yellow" data-sisenote-color="yellow">易错：把相关当因果——两件事同时发生，不代表一个导致另一个</span>

## 五、填表示例

> 现象：客服投诉率上升两成。鱼骨图「法」这一类＝新话术含糊。深挖：话术为何含糊？因为未评审就上线，根因是「上线流程缺少评审环节」。验证：补上评审后抽查，投诉回落。这才是可干预的根因。

> 总结：<span class="sn-red" data-sisenote-color="red">治标只消症状，治本要改机制</span>。深挖加验证，才能让问题不再复发。
